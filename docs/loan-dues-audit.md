# Personal loan DUE section — 2026-10-30

The Owner approved the person-based loan account analysis and requested deployment, including the pending optional Expense reason / details change. `/dues` is a dedicated web section, linked in the menu and Money & dues. Native exposes the same feature in More and Money & dues.

Each saved Person has an account showing total lent, net repayments and current outstanding. Search by name/phone, unpaid/all including cleared filters, per-person lending/repayment/reversal history and Give again / Receive repayment shortcuts are available. Collection chooses an original outstanding loan; repeated loans to the same person stay separate sources but combine in that person's summary. Multiple sources must be collected separately so every receipt has an explicit original loan. Existing custom-contact controls add/edit/archive people; archived people remain collectable but cannot receive new loans. A Staff member's personal loan uses a Person entry, separate from their salary advance. This release does not auto-link account users and contact records by name.

`loanAccounts` is a read projection of authorized state documents. It groups by stable party ID, never by names. It uses exact bigint minor units, excludes cancelled originals from totals, uses current allocated loan due for received/outstanding, and preserves reversed documents in history. Current contact names/phones help lookup; immutable document names/reasons/account/actor/date retain the original transaction. Salary advances, customer dues and supplier refunds are separate workflows and do not enter these totals. Owner sees all history; Staff sees only today's authorized loan sources/history, clearly labeled. Staff cannot collect old loans through a guessed document ID.

All money still posts through the existing PostingService loan/loanRepayment commands, transactions, persisted idempotency, append-only journal and allocations. No new tables, migration, balance overwrite or automatic salary deduction. Cash/Bank decreases only on lending and increases only on actual receipt, with partial amounts allowed. Neither creates sales revenue or expense. Loan overcollection is rejected before Review and authoritatively by PostingService; empty Amount remains deliberate input. New command shortcuts leave persisted uncertain command payloads/keys intact.
