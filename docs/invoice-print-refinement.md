# Invoice print refinement — 2026-10-30

The later [iPhone PDF delivery correction](invoice-pdf-delivery-audit.md) supersedes the browser HTML export path and the rule that legacy Owner/Staff display names render blank. The Owner supplied a new iOS Quartz file showing that the prior desktop-only checks were insufficient for their actual export.

The supplied original PDF has four A4 pages: front on 1, detached thank-you on 2, terms on 3 and detached vector wordmark on 4. That is the observed production failure. The older standalone/wrapper baseline on the current desktop renderer produced two pages, so the audit does not claim every old environment reproduces four. The source also exposed screen-relative container units in print and a broad `.modal footer` rule applying control padding/margins/alignment to the document footers.

## Implementation

- Print uses a 198 x 284 mm canvas inside A4 6 mm margins (285 mm printable height, 1 mm rounding room), literal millimetre units, zero page padding/margins, no size container in print, a single intentional break before the reverse and intact footer blocks. No overflow hiding/cropping, term deletion or document-wide scale reduction. Responsive screen preview retains container units. Modal footer controls are scoped to direct children.
- Item header/body preserve 58/21/21 proportions. One uninterrupted gray relative body contains aligned product rows, two white vertical separators and a single complete inline vector logo. Watermark is positioned 50%/50% with translate(-50%,-50%), 68% body width and 11% opacity; only it is translucent. Artwork uses the approved original contours with a tightly bounded transparent complete logo and distinct gradient IDs.
- Normal model is 13.88 pt/bold, details 11.05 pt in the exported PDF. Actual supplied storage/color, variant and battery/box get separate labeled lines. Bare numeric storage gets GB; existing MB/GB/TB is normalized. Duplicate matching brand/model prefixes are removed. Missing optional specs and unspecified box state are omitted. Amounts remain server decimal strings with BigInt formatting.
- The centered signature block prints saved seller name, line, AUTHORISED SIGN. Actual saved names take priority forever. Only exact legacy role placeholders may resolve from the associated seller profile, never the viewer; unavailable names stay blank. Web/native report missing profile information. Historical records are not rewritten and saved role metadata remains available to authorization/history.
- An optional read-only print collection retains each supplied item's description, quantity and price as aligned rows. The current financial command and receipt API still post one tracked unit; no multi-unit checkout, new calculations or financial workflow is introduced. Primary IMEI/condition and authoritative summary remain the existing sale snapshot.

## Verification

25 hosting/form/render checks and 23 isolated PostgreSQL checks pass, plus API/web builds and all workspace typechecks. Seller tests cover non-placeholder immutable names, placeholders, missing data, correct-profile fallback while another user views, journal immutability and no historical rewrite. Product tests cover duplicate brands, units, omitted fields, zero battery, escaping, multiple rows and unchanged QR modules.

The QA generator renders the real web Invoice component in the real modal/global CSS wrapper, alongside the native/shared standalone HTML. Chromium CLI file rendering and Poppler/pypdf inspection cover the supplied corrected sale plus normal, maximum brand/model, customer/address, seller/variant and money lengths, two products, four normal rows, wrapped two products and native HTML: each output is exactly two A4 portrait pages with complete footers. Ten geometry checks at 900/390 px verify body-centered watermark (maximum error 0.00625 px), all tested rows within the body and clear seller/accounting, warranty/footer and terms/delivery sections. Final PNGs were visually inspected at readable size. The actual rendered QR decodes to the frozen source destination; date and all tested monetary/stock/customer values match the read-only sale projection.

The corrected TT-000005 artifact uses the real saved invoice data, not demo values, and is kept under ignored output/pdf. Its saved seller and associated profile both contain a role placeholder: the name intentionally remains blank. No production mutation was used. The caller can update the corresponding profile through existing Settings; this task does not invent or change the seller's name.

Limits: physical duplex printers, Safari print and physical iOS/Android PDF engines were not exercised. The finite fixed memo cannot promise arbitrary item counts or combinations of unbounded text; tested multi-row cases are print-layout coverage, not a claim of a new multi-item sales feature. No schema migration, role/access change, account reset, paid plan change or synthetic production business records.
