# Authentication

There are exactly OWNER and STAFF roles. There is no registration route/page. Login accepts a normalized assigned User ID or email, plus password. A separate identity table enforces uniqueness across both namespaces, avoiding one person's email becoming another person's login ID. Owner-created login IDs use lowercase letters, digits, dot, underscore or hyphen. Optional emails are normalized server-side.

Configure the requested first Owner using server-only `BOOTSTRAP_OWNER_EMAIL` and `BOOTSTRAP_OWNER_PASSWORD` in the ignored backend `.env` or the deployment secret store. Run `npm run db:bootstrap` after migrations. The bootstrap login ID is `owner`; the exact configured email also works. The supplied brief is the source of the requested initial credentials; it is deliberately not committed. Local ignored configuration has been prepared from that input.

Bootstrap locks the shop row and succeeds only once. It creates one Owner, the approved expense labels and an audit event, with no business records or sample staff. Reruns do not reset passwords, repopulate archived categories, or recreate accounts. Existing users with incomplete bootstrap state cause an explicit review failure, not an overwrite. Concurrent bootstrap is tested.

Passwords use bcrypt cost 12, with a server-enforced 72-byte UTF-8 limit to prevent silent bcrypt truncation. New passwords require at least eight characters. Initial/reset passwords require a change before normal APIs. Users must supply their current password to change it. Successful change revokes every session and requires a new login. Owner resets assign a new initial password; they also revoke sessions and require change. Account role changes/deactivation revoke sessions. The last active Owner is protected by an advisory lock and count under the same transaction. Owners may create multiple Owners and Staff. Sensitive mutations are audited without passwords.

Opaque random 256-bit session tokens are stored only as SHA-256 hashes on the server. Sessions expire after 30 minutes and have a seven-day absolute limit. Refresh rotates the token and extends only within that limit. Web sessions use HttpOnly, SameSite Strict cookies and Secure in production; native uses Bearer tokens in Expo SecureStore with device-only unlocked access. No auth secret is stored in localStorage/AsyncStorage. Logout deletes the server session. A network error does not erase a valid session or unsaved draft; a confirmed 401 requires login.

Cookie mutations require an allowlisted Origin; CORS origins are explicit. Deploy web/API under the same HTTPS site using the provided reverse proxy. Do not change to cross-site cookies without reviewing CSRF and cookie policy. Login attempts are rate limited using database counters keyed by a digest of IP and normalized identity. API errors/logs avoid password/token/database-value output. JSON request size is limited. HTTPS and trusted reverse-proxy configuration remain deployment responsibilities.

Tests cover first-login enforcement, private user creation, unauthorized creation/role escalation, identity normalization, bootstrap reruns, password/reset session revocation, deactivation, last Owner, browser cookie flags, CSRF Origin rejection and monthly report/export authorization.
