# Optional purchase evidence — 2026-11-02

The Owner approves implementation/audit/deployment of optional Supplier purchase memo photos and optional individual-seller NID front/back photos. The controls must match existing form dimensions. No OCR, identity verification or image on sales invoices is requested.

## Storage and permissions

Migration 012 adds private `purchase_image` bytes and `purchase_image_link` metadata only. It does not update existing accounts, documents, inventory, journals or snapshots. RLS is enabled and all PUBLIC/Supabase Data API role grants revoked, just like the other Nest-owned tables. Images are absent from ordinary state, reports and receipt snapshots. Every file/list/link/remove request authenticates; saved evidence follows Owner-all / Staff-today purchase dates. Unbound images are readable/linkable only by their uploader for 24 hours. Account permissions are not inferred from a file URL. No public bucket, permanent public URL or client service credential.

Compressed JPEG bytes use the existing private PostgreSQL storage, including the normal database backup/restore path, rather than adding an unconfigured object-storage account/key or keeping files on Render's ephemeral disk. This is bounded small-shop evidence storage: max 512 KiB per encoded image, four active memo pages per supplier purchase, independently optional one front and one back per individual purchase. The combined image-byte budget is 128 MiB to leave room for the accounting data on the current Free database; uploading stops with an explicit error at that budget, without changing balances or forcing an image on new purchases. Removed evidence remains available to Owner in removal history and still counts toward storage. This budget is not a provider storage guarantee; normal database quota/backups still require monitoring. A larger photo archive should move bytes to private object storage with an explicitly configured server credential, retaining these purchase references/permissions. No paid upgrade is performed.

Browser camera/gallery input is preprocessed to JPEG, up to 2200×3000 inside bounds, with size-adaptive quality. The API independently decodes only JPEG/PNG/WebP, enforces bytes/pixels, reorients/re-encodes and strips metadata. SVG, undecodable files, oversized bodies and multi-page content are rejected. Original full-resolution files are not retained. The preview and authenticated full-image link let the operator check legibility before posting. Camera capture is an OS/browser hint, not a guarantee that every device opens the same picker. Unsupported iPhone HEIC files need conversion/selection as JPEG/PNG.

## Accounting and recovery

Images are uploaded first, and their opaque IDs live in a separate per-account draft/pending sidecar. The existing financial command data/hash/key is unchanged, including legacy pending entries. A successful purchase ID is persisted before attaching evidence. If that metadata transaction fails, the UI explicitly says the purchase is saved; retry/reload retries only association. Check-status recovery also retains the same images. Continuing without photos is deliberate, and photos can be added later in Purchase Details. Atomic link/audit transactions, original upload IDs and same-document link retries prevent duplicate records. Linking does not permit a memo on an individual purchase, an NID on a supplier purchase, duplicate NID sides, another actor's staged image or an image already assigned elsewhere. Soft removal is audited; a late retry does not reinstate removed evidence. Expired/unbound uploads are pruned when a new upload arrives. New and existing purchase accounting remains solely PostingService's responsibility.
