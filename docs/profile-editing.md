# Owner / Staff profile editing — 2026-10-30

Settings → **My profile** shows the signed-in account's name, User ID, email and role. **Edit profile** updates name, User ID and optional email. **Change password** remains a separate current/new-password form in the same section. Web and native clients share validation and identity-change detection.

OWNER and STAFF can edit themselves through authenticated `PATCH /auth/profile`. That strict schema rejects ID, role, active, password and other account-control fields. Only the existing authenticated account ID is used. A display-name edit keeps sessions. A User ID/email change requires the caller's current password, atomically replaces the login aliases, revokes all account sessions, clears the web cookie or native token, and asks for login with the updated identity. Password changes retain the existing current-password check and session revocation. A cleared email removes that login alias; the required User ID remains usable.

Owner user management also has Edit profile. Owners can edit account names and, with their own current Owner password, update an account's login identity. Staff cannot use that administration endpoint. Existing role/active/password controls and last-Owner protection remain. Display-name edits do not revoke sessions; actual access/credential changes do. No public registration, recovery-by-unverified-email flow, new role or new permission category was introduced.

All account mutations serialize on the existing account advisory lock and lock actor/target rows. The existing login path now rechecks the selected identity under the user-row lock so a removed alias cannot complete an in-flight login after identity replacement. Existing unique account/identity constraints decide duplicate and concurrent collisions. Failures roll back profile, aliases, role and audit changes together. Audit records include before/after profile metadata and change flags, never passwords, password hashes or session tokens. Public responses remain explicitly whitelisted.

User UUIDs are stable. Posted actor names, seller roles, invoices and append-only financial records remain unchanged. New sales snapshot the updated account name. No schema migration or Supabase grants change is required.
